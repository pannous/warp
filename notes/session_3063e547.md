## Philosophical Analysis

### Three Distinct Concepts with Different Semantics:

**1. Pair(a, b)** - Binary structural relationship
- Examples: `1:2`, `x:y`, `(key, value)`
- Meaning: Two things in relationship, order matters
- JSON: `[a, b]` - natural, reversible
- Use: Tuples, cons cells, structural pairing

**2. Key(string, value)** - Named binding
- Examples: `name: "Alice"`, `age: 30`  
- Meaning: String label → value mapping
- JSON: `{"name": "Alice"}` - native representation
- Use: Object properties, named parameters, dictionaries

**3. Tag(title, params, body)** - Triple structure for syntax
- Examples: `if(condition){body}`, `<div class="x">content</div>`, `defun(name, args){body}`
- Meaning: Named operation with parameters AND body
- JSON: `{"_tag": "if", "_attrs": condition, "_body": {...}}` - awkward
- Use: HTML/XML, function syntax, control structures

### The Unification Dilemma

**Option A: Merge Key into Pair**
```rust
// Key becomes: Pair(Text(string), value)
Pair(Box::new(Text("name")), Box::new(Text("Alice")))
```
✅ Simpler structure
❌ Loses type enforcement (keys could be non-strings)
❌ JSON mapping becomes ambiguous: `["name", "Alice"]` vs `{"name": "Alice"}`

**Option B: Keep all three separate (current)**
```rust
Key("name", Box::new(Text("Alice")))    // {"name": "Alice"}
Pair(Number(1.1), Text("forbidden"))     // [1.1, "forbidden"]  
Tag { title: "div", params: ..., body: ... }  // complex object
```
✅ Semantic clarity
✅ Type safety
❌ More node variants
❌ Tag JSON representation still awkward

**Option C: Tag as nested Pair**
```rust
// Tag(title, params, body) becomes:
Pair(Text(title), Pair(params, body))
```
❌ Loses semantic meaning
❌ Can't distinguish `(title, (params, body))` from Tag syntax
❌ No improvement for JSON mapping

### The JSON Representation Problem

Current mappings expose asymmetry:
```javascript
// Round-trip friendly:
Node::Key("x", 42)    <-> {"x": 42}           ✅
Node::Empty           <-> null                ✅
Node::List([1,2,3])   <-> [1,2,3]             ✅

// Lossy:
Node::Pair(1.1, "x")  -> [1.1, "x"]           ⚠️ (could be List)
Node::Tag{...}        -> {"_attrs": ...}       ⚠️ (magic fields)
```

### Elegant Solution Space

**Proposal: Embrace the semantic distinction, improve JSON consistency**

1. **Keep Pair, Key, Tag separate** - they represent different concepts:
   - Pair = structural tuple (math, cons cells)
   - Key = named binding (objects, maps)  
   - Tag = ternary syntax node (HTML, functions, AST)

2. **Standardize JSON representation with metadata**:
   ```json
   // Pair with non-string key
   {"_pair": [1.1, "forbidden"]}
   
   // Tag with full structure  
   {"_tag": "if", "_params": {"condition": true}, "_body": {...}}
   
   // Or more compact Tag when params are Empty:
   {"if": body}  // params = Empty
   ```

3. **Document the semantic contracts**:
   - Pair: Use for cons cells, tuples, structural relationships
   - Key: Use when you want JSON object semantics
   - Tag: Use for syntax trees, HTML, parameterized blocks

### The Deep Question

**Is `Key` just `Pair(String, value)` with restrictions?**

**Arguments for merger:**
- Simpler mental model
- Fewer node types
- Key is technically a specialized Pair

**Arguments against:**
- JSON has native object syntax - we should honor that
- `{"name": "Alice"}` is fundamentally different from `["name", "Alice"]`
- Type system can enforce string keys with Key variant
- Semantic intention: Key means "this is an object property"

**My philosophical take:**
The distinction between Key and Pair mirrors the distinction between JSON objects and arrays - one is for **labeled data**, the other is for **sequential/structural data**. Collapsing them would be like saying "objects are just arrays with string keys" - technically true, but semantically muddled.

Tag is the interesting one - it doesn't map cleanly to either, because it's genuinely **ternary**. This suggests it might deserve special treatment in both the Node structure AND JSON representation.

What's your intuition? Should we prioritize:
1. **Structural minimalism** (fewer node types, more expressive power)
2. **Semantic clarity** (explicit types for different use cases)
3. **JSON fidelity** (make round-tripping perfect, even if it adds complexity)
